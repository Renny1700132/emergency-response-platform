# ADR-001：应用拆分与部署单元

- 文档编号：YJGL-G3-07-ADR-001
- 状态：Proposed（待 A/C 复核与人工接受）
- 日期：2026-09-18
- 决策主责：B
- 复核：A、C
- 对应候选：ADC-001
- 关联设计：G3-01R §5—§6、G3-03、G3-05
- 关联要求：PE-01—PE-12、NFR-REL-01—03、NFR-MNT-02、KN-005、KN-028、G2-FR-028

## 1 背景

本系统包含预案、事件、任务、态势、资源、值班、演练、知识、移动端组合、外部集成和平台横切模块。统一中台提供身份、组织、权限、消息、工作流、文件、门户和数据汇聚；本项目只做业务适配。系统采用私有化容器部署，峰值在线用户要求不少于 100 人，非乙方人员应在干净环境一次部署成功且不超过 2 小时。

当前规模需要清楚的数据主责、单领域事务和外部协议隔离，但没有证据证明必须承担微服务的分布式事务、服务发现、跨服务追踪和多部署单元运维成本。甲方基础环境、节点规模、高可用平台和团队长期运维能力尚未确认，因此本决策不能把具体框架、容器编排产品或物理节点写成既定事实。

## 2 待决问题

应急管理业务首个可交付版本采用模块化单体、领域微服务，还是由统一中台工作流主导的轻业务适配？如何在满足模块隔离、故障降级、可测试和两小时部署要求的同时保留未来拆分路径？

## 3 决策驱动因素

| 因素 | 约束或证据 | 判定重点 |
| --- | --- | --- |
| 业务一致性 | 事件启动、任务生成、状态历史和 Outbox 需原子提交 | 减少跨服务事务和中间状态 |
| 外部依赖 | 视频、消息、定位、门禁、消防、入侵、IoT、中台均需适配 | 协议必须隔离，故障不得扩散到核心事实 |
| 部署运维 | 私有化容器部署；干净环境≤2小时 | 部署单元、配置和排障复杂度可控 |
| 性能容量 | 峰值≥100在线；多项秒级指标 | 可通过进程内调用、索引、投影和异步副作用支撑，仍待压测 |
| 演进 | 专业接口可能独立升级或形成热点 | 保留端口和事件边界，允许证据驱动拆分 |
| 证据状态 | 真实部署资源和部分接口证据未齐 | 不以推测冻结微服务或中台能力 |

## 4 候选方案

### 4.1 方案 A：模块化单体 + 端口适配 + 持久化异步任务（建议采纳）

核心业务部署为少量应用单元，代码和数据访问按 MOD-PLAN—MOD-PLATFORM 强隔离。模块只能经应用服务、领域事件和明确定义的查询接口协作；外部系统经独立端口/适配器接入。业务事实同步提交，通知、投影、报表等副作用经事务 Outbox 和持久任务异步执行。

优势是单领域事务清楚、部署与排障成本较低，并能复用统一中台而不把业务规则散落到外部平台。主要风险是团队若绕过模块边界直接跨域写表，系统会退化为耦合单体，因此必须用依赖规则、数据所有权和契约测试约束。

### 4.2 方案 B：领域微服务 + 事件驱动（本期不建议）

按事件、任务、资源、演练、集成等拆成独立服务和独立数据主责，通过 API 与事件协作。它提供更强的故障隔离和独立扩缩，但会引入分布式事务、事件版本、服务发现、跨服务可观测、更多部署单元和测试环境。

当前峰值规模、故障证据和甲方编排平台资料不足以证明收益大于成本。若直接采纳，会提高两小时干净部署和 MTTR≤2小时的风险。

### 4.3 方案 C：统一中台工作流主导 + 轻业务适配（本期不建议）

尽量把流程、状态和通知交给甲方中台，本系统只保留页面与薄适配。该方案可减少通用能力建设，但中台具体 API、版本、超时、审计和性能证据尚未取得，无法证明能承载事件核实、任务状态、盘点快照、打卡幂等和控制命令等领域不变量。

## 5 建议决策

建议采用方案 A，状态保持 Proposed：

1. 核心业务以模块化单体为逻辑架构，初始部署单元为应用服务、H5/静态资源、关系数据库及甲方提供的外部能力；物理节点和产品待环境确认。
2. 每个业务模块拥有自己的表和写入服务，其他模块不得直接写其数据；跨模块查询优先使用只读投影或应用接口。
3. MOD-INTEGRATION 通过 EXT-VIDEO、EXT-PUBLISH、EXT-INTRUSION、EXT-ACCESS、EXT-FIRE、EXT-IOT、EXT-MIDDLE、EXT-MESSAGE 等端口隔离外部协议。
4. 领域事件、OpenAPI 和数据主责作为未来拆分接缝。只有压测、故障或升级频率证据满足触发条件时才拆分部署单元。
5. 本 ADR 不选择具体 Web 框架、数据库品牌、消息中间件、缓存产品或容器编排产品；这些选择须由后续证据或独立 ADR 决定。

## 6 后果

### 6.1 正面后果

- 事件启动、任务生成、状态历史和 Outbox 可在单库事务中保持一致。
- 部署单元较少，有利于干净环境部署、备份恢复和故障定位。
- 端口适配屏蔽厂商协议变化，统一中台能力可复用而不重复建设。
- 模块 ID、接口和领域事件为 G3-08、测试及未来拆分提供稳定追踪点。

### 6.2 负面后果与缓解

| 负面影响 | 缓解措施 | 验证 |
| --- | --- | --- |
| 进程故障影响多个模块 | 关键状态持久化、健康检查、容器重启、外部依赖隔离 | 故障注入与恢复演练 |
| 跨模块直接访问造成耦合 | 模块依赖白名单、数据主责检查、代码评审门禁 | 静态依赖扫描与架构测试 |
| 热点模块不能独立扩容 | 态势投影、外部适配保持可拆分接口 | PE-01—12 压测与资源曲线 |
| 单库容量或锁竞争 | 索引、短事务、慢查询门禁、容量监测 | PE-07、PE-11、PE-12 与并发写测试 |

## 7 验证与接受条件

1. 架构测试证明模块依赖无反向环、跨模块无直接写表。
2. 在受控数据规模和峰值不少于 100 在线用户下执行 PE-01—12 相关测试，记录响应、错误率和资源使用；未实测前不宣称达标。
3. 非乙方人员按部署手册在干净环境一次部署，并记录是否在 2 小时内完成。
4. 注入外部接口超时、应用进程重启和数据库短暂不可用，验证事实不丢失、任务可恢复、告警和人工降级可追踪。
5. A 复核总体与计划一致性，C 复核需求、★、数字和责任边界；人工接受后方可把状态改为 Accepted。

## 8 重新评估触发条件

- 单一模块的资源占用长期成为瓶颈，且独立扩缩能由压测量化证明收益；
- 厂商 SDK 崩溃、升级频率或安全隔离要求需要独立进程；
- 甲方提供成熟服务编排、消息和可观测平台，并确认多服务运维责任；
- 单库事务或发布节奏成为可重复的交付阻碍；
- 业务规模、并发或可用性目标经变更流程显著提高。
