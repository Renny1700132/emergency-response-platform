# ADR-002：业务提交与异步副作用一致性

- 文档编号：YJGL-G3-07-ADR-002
- 状态：Accepted（2026-09-18 用户最终准出授权；A/C Review PASS；技术验证与重开条件仍有效）
- 日期：2026-09-18
- 决策主责：B
- 复核：A、C
- 对应候选：ADC-002
- 关联设计：G3-04 `em_outbox_event`、G3-05 UnitOfWork/OutboxDispatcher、G3-06 领域事件信封
- 关联要求：G2-FR-003、011、014、015、020、022、027、029；G2-RCLR-001、002、003、008；PE-01—04；NFR-REL-01—03

## 1 背景

启动预案、事件核实、任务生成、缺卡告警和外部告警接入都需要先形成不可丢失的业务事实，再派生消息、态势投影或外部调用。外部平台可能超时、返回迟到或重复回执，应用进程可能在业务提交后、发送前退出。若把数据库提交与外部发送放在同一长事务中，会扩大锁和故障范围；若采用尽力发送，进程故障会形成“业务已成功但通知永久丢失”。

门禁开启属于控制命令：必须由授权人员确认、服从既有安全联锁，失败后告警并人工降级。其超时结果可能未知，不能套用普通通知的自动重试。

## 2 待决问题

业务事实与通知、投影、报表和外部调用之间采用事务 Outbox/持久任务、分布式事务，还是提交后尽力发送？如何区分可安全重试的普通副作用和禁止自动重放的控制命令？

## 3 候选方案

### 3.1 方案 A：事务 Outbox + 持久任务（建议采纳）

在同一业务事务中写领域事实、状态历史、审计摘要和 Outbox 事件。提交后由 Dispatcher 使用租约领取任务，按策略调用适配器；成功记录终态，失败按受控退避重试或进入人工处置。消费者以 `eventId` 或业务幂等键去重。

### 3.2 方案 B：跨数据库与外部系统分布式事务（否决候选）

用两阶段提交或全局事务协调业务库与外部系统。甲方既有视频、消息、门禁等平台是否支持事务协议没有证据；网络分区会延长锁持有并扩大不可用面。该方案不适合开放外部接口边界。

### 3.3 方案 C：业务提交后尽力发送（否决候选）

事务提交后在请求线程直接调用外部平台，失败只记日志或返回错误。实现简单，但应用在提交后退出会永久丢失通知，重试请求又可能重复改变业务状态，无法满足可追踪和恢复要求。

## 4 建议决策

建议采用方案 A，状态保持 Proposed：

1. 每次领域命令只跨一个领域写事务；事实、状态历史、幂等记录、必要审计摘要和 Outbox 同事务提交。
2. Outbox 事件包含 `eventId`、`eventType`、`schemaVersion`、聚合标识、四类时间、`traceId` 和最小必要载荷；禁止写入明文凭据和不必要敏感数据。
3. Dispatcher 使用短租约领取、心跳/过期回收和指数退避；最大尝试次数与间隔配置化，不能新增未经裁决的固定业务时限。
4. 普通通知、态势投影和可证明幂等的查询/回执可重试；每次尝试、响应时间、结果和脱敏错误摘要均留痕。
5. 门禁等控制命令不进入通用自动重试。超时标记 `RESULT_UNKNOWN`，触发告警、回执对账和人工确认；只有新的授权确认和一次性令牌才能再次下发。
6. 重复或迟到回执通过平台消息 ID、尝试号和幂等键关联原记录；终态业务不得因迟到回执重复迁移。
7. 本 ADR 不指定消息中间件产品。初始实现可使用数据库 Outbox 与持久任务；若后续采用消息代理，Outbox 仍作为事实提交与发布之间的可靠接缝。

## 5 失败模型与处理

| 失败点 | 可观察状态 | 恢复/降级 | 禁止行为 |
| --- | --- | --- | --- |
| 业务事务回滚 | 无业务事实、无 Outbox | 返回稳定错误码 | 不得单独发送外部消息 |
| 提交后进程退出 | Outbox=PENDING | 重启后租约领取 | 不得依赖内存队列 |
| 外部调用超时 | 尝试=TIMEOUT | 普通通知退避；控制命令转人工 | 不得把超时当成功；控制命令不得盲重试 |
| 重复投递 | 相同 eventId/幂等键 | 返回首次结果或忽略重复副作用 | 不得重复创建事件、任务或打卡 |
| 迟到/乱序回执 | 关联原消息和尝试 | 追加历史，按状态规则更新投递终态 | 不得覆盖历史或重复触发业务状态 |
| 消费者长期失败 | DEAD/人工处置 | 告警、诊断、授权后重放 | 不得静默丢弃 |

## 6 后果

### 6.1 正面后果

- 业务事实和待执行副作用不会在进程故障间形成不可追踪空窗。
- 外部依赖故障不延长核心业务事务，事件与任务仍可查询和人工处置。
- 重试、迟到、重复和人工降级均能形成验收与运维证据。
- 态势投影可重建，不反向成为业务事实源。

### 6.2 负面后果与缓解

| 负面影响 | 缓解措施 | 验证 |
| --- | --- | --- |
| 最终一致导致短暂延迟 | UI 显示投递/投影状态；PE 预算按端到端时间实测 | PE-01—04、PE-10 |
| Outbox 表增长 | 状态/时间索引、归档、积压监控 | 容量与慢查询测试 |
| 消费者重复执行风险 | 幂等键、唯一约束、条件状态迁移 | 重复投递与并发测试 |
| 错误重试造成外部压力 | 分类错误、退避、熔断和最大尝试配置 | 429/5xx/超时故障注入 |

## 7 验证与接受条件

1. 在提交前、提交后发送前、发送后记账前分别注入进程退出，证明事实、Outbox 和投递记录可恢复且无静默丢失。
2. 对相同启动、告警、扫码和回执重复提交，证明业务对象不重复、首次结果可回取。
3. 对回执乱序和迟到执行状态表驱动测试，证明历史保留且终态不重复迁移。
4. 对门禁超时证明没有自动二次下发，页面出现结果未知、告警和人工处置入口。
5. 对消息正常验收通道执行不少于 20 路并发及到达率统计；真实证据缺失时保持 `ISSUE-G3-01-001` OPEN。
6. A/C 复核通过并完成人工接受后，状态方可改为 Accepted。

## 8 重新评估触发条件

- Outbox 积压或数据库轮询成为经压测证明的瓶颈；
- 甲方提供受控消息代理并要求统一事件基础设施；
- 新增跨系统强一致业务且补偿无法满足；
- 外部接口提供明确幂等协议或改变控制命令安全语义；
- 关键 PE、可用性或恢复目标经变更流程调整。
