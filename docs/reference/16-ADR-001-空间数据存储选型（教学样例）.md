# ADR-001 空间数据存储：采用 PostgreSQL + PostGIS

- 状态：已接受（V3.0 校订，2026-08-26，设计评审会通过）
- 决策人：架构组（3 人）+ 需求负责人
- 关联需求：FR-06.1（矢量化三格式）、FR-06.3（图斑编辑）、FR-06.6（面积统计误差≤3%）、AC-FR-02.1-b（面积加权完整率/正确率评估）、FR-01.2（影像空间范围检索）、FR-07.2（卷帘对比叠加）
- 关联文档：数据库设计说明书 V3.0、RTM v3

## 背景（Context）

平台需同时管理结构化业务数据（用户、任务、日志、参数）与空间数据（影像范围、分割图斑、编辑几何）。三条链路对空间能力提出硬要求：① 影像按空间范围+属性联合检索（FR-01.2）；② 图斑的编辑、拓扑校验与面积统计（FR-06.3/06.6，面积误差≤3% 须可验证）；③ 精度评估的面积加权叠加运算（AC-FR-02.1-b，完整率≥80%、正确率≥85% 按面积加权计算）。空间数据的存储与计算能力是一期架构的基础决策。

## 候选方案

### 方案 A：PostgreSQL + PostGIS（采纳）
开源关系库+空间扩展，原生支持 geometry/geography 类型、GIST 空间索引、ST_Intersects/ST_Area/ST_Union 等空间函数；面积加权叠加计算可在库内完成。

### 方案 B：纯文件存储 + 关系库元数据（否决）
影像范围与图斑矢量全部以 Shapefile/GeoJSON 文件存对象存储，关系库只存文件索引。
否决理由：① 空间联合检索需读文件逐个解析，FR-01.2 的『空间+属性联合过滤』在万级影像记录下无法保证浏览性能（PE-04 影像浏览≤2s）；② FR-06.6 面积统计与 AC-FR-02.1-b 的面积加权叠加需全部加载进内存计算，无法在线完成；③ 事务一致性差——结果集记录与矢量文件可能出现孤儿引用，与审计可追溯要求冲突。

### 方案 C：MongoDB（否决）
文档库原生支持 GeoJSON 与 2dsphere 索引。
否决理由：① 空间分析函数远弱于 PostGIS（无成熟的面积加权、拓扑谓词体系），AC-FR-02.1-b 的四则面积加权指标无法库内完成；② 业务数据（任务→结果集→图斑溯源链）为强关联模型，不适合文档模型；③ 团队既有的 PostgreSQL 运维与备份方案（FR-10.5）可直接复用，引入第二套数据库增加运维面。

## 决策（Decision）

采用方案 A：PostgreSQL 14 + PostGIS 3.3。空间字段统一 CGCS2000（EPSG:4490）存储，对外交互按 EPSG:4326 转换；空间索引用 GIST；面积统计与精度评估叠加计算下沉库内（详见数据库设计 V3.0 第 4 章、详细设计 V3.0 M-06）。

## 后果（Consequences）

- 正面：空间检索、编辑拓扑校验、面积统计与精度评估均有成熟支撑；事务一致性覆盖业务+空间数据；运维栈统一。
- 负面：PostGIS 对团队有学习成本（安排迭代 1 启动前集中培训 0.5 人日，见 plan.md 迭代 1）；库内叠加计算在大结果集（>50 万顶点）时须防长事务——已在详细设计 M-06 加顶点数熔断（超限转离线批处理）。
- 备注：决策依据全部为需求条款与可验证指标，不以团队熟悉度为依据。
