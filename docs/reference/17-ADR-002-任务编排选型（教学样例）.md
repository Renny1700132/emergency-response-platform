# ADR-002 任务编排：采用 Celery + Redis（GPU 独占队列模型）

- 状态：已接受（V3.0 校订，2026-08-26，设计评审会通过）
- 决策人：架构组
- 关联需求：FR-05.2（GPU 资源独占、排队串行）、FR-05.3（进度回报）、FR-05.4（失败重试）、FR-05.5（任务归档）、PE-06（并发 1 推理+30 在线）、PE-01（交互响应≤3s）
- 关联文档：概要设计 V3.0 第 3 章、详细设计 V3.0 第 6 章（M-05）

## 背景

全自动分割（1km²≤10min，PE-02）、文本批量分割（≤5min，PE-03）、时序批量与导出均为长耗时任务，必须与 Web 请求解耦；同时交互式分割要求 P95≤3s（PE-01），不能被批量任务饿死。SRS 明确规定 GPU 资源独占、任务排队串行执行（FR-05.2），且需支持进度回报、取消、失败重试与归档（FR-05.3/05.4/05.5）。任务编排模型直接决定 FR-05.x 整组条款能否成立。

## 候选方案

### 方案 A：Celery + Redis（采纳）
Python 生态标准分布式任务队列；支持优先级、定时、重试、取消（revoke）；与后端技术栈（FastAPI/Python）同语言。队列划分：**gpu_queue（GPU 独占串行，全自动/文本批量/时序批量共用，FR-05.2）、interactive_channel（交互推理独立低延迟通道，PE-01）、tile_queue（金字塔构建）、export_queue（成果导出）** 四类隔离。

### 方案 B：自研调度器（否决）
基于数据库轮询+自写进程管理实现队列。
否决理由：① 四周工期内自研调度器的正确性风险不可控（任务丢失、重复执行、僵尸 Worker 三类故障各需专门设计与测试投入）；② FR-05.4 的重试退避、FR-05.5 的归档转移在自研方案中都是新开发项，而 Celery 为内建能力；③ 无可复用的社区运维经验，违背『朴素优先』设计原则——复杂度须有 ADR 论证，此处复杂度无收益。

### 方案 C：Airflow（否决）
面向数据管道编排的 DAG 调度系统。
否决理由：① Airflow 的设计目标是定时批处理 DAG，任务触发延迟在秒级~分钟级，无法满足用户触发的在线任务即时派发（FR-05.1 创建后应立即入队）；② 其调度语义面向『数据血缘管道』而非『在线任务』，FR-05.3 实时进度推送需额外开发；③ 引入整套 Airflow 部署（Scheduler/Webserver/Metadata DB）使最小部署节点数翻倍，超出教学环境资源约束。

## 决策

采用 Celery + Redis，四队列隔离：gpu_queue 独占串行（并发度=1，直接实现 FR-05.2 的 GPU 独占语义）；interactive_channel 不走 gpu_queue，由常驻交互 Worker 独立消费，保障 PE-01 不被批量任务影响；tile_queue 与 export_queue 使用 CPU Worker。Worker 心跳供 FR-08.4 熔断判断。

## 后果

- 正面：GPU 独占语义由队列并发度天然保证，无自研锁逻辑；优先级/取消/重试内建；四队列隔离直接支撑 PE-01 与 PE-06 并存场景。
- 负面：Redis 单点为队列可用性瓶颈——缓解：Redis 持久化 AOF+任务幂等设计（任务可安全重入，详细设计 M-05）；gpu_queue 独占串行意味着大批量任务排队时间长——缓解：FR-05.6 邮件通知+进度页明确排队位次，需求确认书已向甲方说明该取舍。
