## 背景

分割推理是长耗时操作：点提示单轮秒级（PE-01 ≤3 s），全自动分割分钟级（PE-02 ≤10 min），文本提示分钟级（PE-03 ≤5 min）。REST 接口若同步阻塞，长任务会顶住连接；投标阶段的技术方案因此写了「Celery + Redis 异步任务队列 + 任务状态轮询接口」。

设计评审提出两个问题：**这个队列的调用方是谁？** 以及 **它把哪一条需求的哪一个指标改善了？** 两个问题当场都没答上来，触发本次决策。

## 待决问题

REST 分割接口用同步阻塞、异步任务队列，还是两者混合？

## 候选方案

| 方案 | 长任务处理 | 新增组件 | 客户端复杂度 | 失败可见性 |
| --- | --- | --- | --- | --- |
| A. 同步阻塞 + 模型缓存 | 请求内完成，超时由客户端控制 | 无 | 低（一次请求拿结果） | 高（错误直接返回） |
| B. Celery + Redis 异步队列 | 提交任务返回 ID，轮询状态 | Redis + Worker 进程 | 高（提交、轮询、取结果三步） | 中（需查任务表） |
| C. 混合：短任务同步、长任务异步 | 按预估耗时分流 | Redis + Worker | 最高（两套语义） | 中 |

## 决策

**采用方案 A：同步阻塞 + 模型实例缓存。**

- 三个分割端点（`/segment/automatic`、`/segment/predict`、`/segment/text`）均在请求内完成并直接返回结果；
- 通过**模型实例缓存**消除主要耗时来源——缓存键为「模型版本 + 模型 ID + 冻结后的构造参数」，不同配置分别缓存互不覆盖；
- 长任务的批量场景走 **CLI 侧**（`segment automatic` 等子命令），而不是让 REST 承担批处理职责。

## 理由

1. **调用方决定形态。** 本期 REST 的调用方只有两类：QGIS 插件（交互式，用户在界面前等结果）和冒烟脚本。两者都要求"发一次拿一次"，异步 API 反而要求它们实现轮询逻辑——把复杂度从服务端搬到了客户端，总量还增加了。
2. **真正的性能瓶颈是模型加载，不是排队。** 实测中首次加载 SAM 模型占端到端耗时的大头，第二次起命中缓存后 PE-01 从超标回落到达标。队列解决的是"并发请求排队"，而本期的瓶颈是"重复加载"——**队列治不了这个病，缓存能治。**
3. **异步队列会引入新的失败模式。** 任务丢失、状态不一致、Worker 假死、结果过期清理，每一样都要写代码、写测试、写运维文档。REL-03（临时目录零残留）在同步模型下只需一个 `finally`，在异步模型下要处理 Worker 崩溃后的孤儿目录。
4. **DT-01★ 是硬约束。** 引入 Redis 与 Worker 意味着干净环境部署从"起一个进程"变成"起三个进程 + 配连接串"，30 分钟部署目标风险陡增。

## 后果

**正面**：无新增常驻组件；错误直接以 HTTP 状态码返回，REL-02 的四类非法输入用例得以简单实现；`_cleanup_tmpdir` 在请求生命周期内闭环，REL-03 可验证。

**负面与缓解**：

| 负面影响 | 缓解措施 |
| --- | --- |
| 单个长请求占用连接，高并发下吞吐受限 | 本期为单用户工具，无并发指标要求；并发场景纳入 HLD 附录 B |
| 客户端需设置足够长的超时 | 部署与运维手册（45）明确各端点建议超时值；QGIS 插件侧配置化 |
| 全自动分割超大影像可能超出网关超时 | 大幅面走 CLI 分块路径（FR-02.4），REST 端在文档中标注单次输入尺寸建议上限 |

**重新评估的触发条件**：出现以下任一情形时重开本决策——并发用户数进入需求、单次任务常态超过 10 分钟、需要任务重试与断点续跑。

## 教学备注

投标阶段写「Celery + Redis」不丢人，**设计阶段没有复核它才丢人**。技术方案在投标时可以是候选集，但进入设计就必须逐项回答"解决哪条需求的哪个指标"。这次的复核结论是砍掉，下次可能是保留——重要的是那个提问动作是否发生过，以及它的答案有没有被写下来。
