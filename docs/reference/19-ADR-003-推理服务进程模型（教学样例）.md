## 背景

系统需支持三代分割模型共 9 个变体（SAM v1 三个、SAM 2 四个、SAM 3 两个），外加 FastSAM、HQ-SAM、LangSAM 三类扩展。模型权重体积大、加载慢、显存占用高，而 PE-01 要求点提示单轮响应 ≤3 s——**首次加载就会吃掉整个预算**。

同时 REL-01 要求：某个模型的可选依赖未安装时，系统给出准确的安装提示而不是崩溃。这意味着模型不能在服务启动时全量预加载。

## 待决问题

推理服务用什么进程模型？模型实例何时加载、如何复用、如何隔离不同配置？

## 候选方案

| 方案 | 加载时机 | 复用方式 | 显存占用 | 配置隔离 |
| --- | --- | --- | --- | --- |
| A. 启动时全量预加载 | 服务启动 | 全局单例 | 最高（9 个变体全驻留） | 无需隔离 |
| B. 每请求新建实例 | 每次请求 | 不复用 | 最低 | 天然隔离 |
| C. 单进程 + 按配置键缓存 | 首次使用时惰性加载 | 按缓存键复用 | 中（按需驻留） | 靠缓存键保证 |
| D. 多进程 Worker 池，每进程绑定一个模型 | 池启动时 | 进程内复用 | 高 | 进程级隔离 |

## 决策

**采用方案 C：单进程 + 惰性加载 + 按配置键缓存。**

缓存键 = `(模型版本, 模型 ID, 冻结后的构造参数)`。构造参数需先做**顺序无关的冻结**处理，保证 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 命中同一缓存项。

另提供 `DELETE /models` 端点主动清空缓存，用于释放显存与故障恢复。

## 理由

1. **方案 A 与 REL-01 直接冲突。** 启动时全量加载意味着任何一个模型的 extras 缺失都会导致服务起不来——而 REL-01 要求的恰恰是"缺依赖时优雅提示、其余功能照常"。惰性加载让依赖检查发生在真正用到该模型的那一刻。
2. **方案 B 让 PE-01 不可能达标。** 每请求重新加载模型，交互分割的每一轮都要付出加载代价，3 秒预算连一半都不够。
3. **方案 D 的隔离收益本期用不上。** 多进程池能防止单模型崩溃拖垮整个服务，但代价是显存成倍占用与进程间通信复杂度。本期是单用户工具，没有"一个用户的崩溃影响另一个用户"的场景。
4. **配置隔离必须靠缓存键，不能靠全局变量。** 这是本决策最容易出错的地方：用单个全局 `_model` 变量缓存，第二次不同配置的请求会拿到上一次的实例，产生**静默错误**——结果看起来正常，实际用错了模型。因此把它固化为 `constitution.md` R-10，并配两条专门的回归测试守着。

## 后果

**正面**：PE-01 在缓存命中后达标；REL-01 可实现；显存占用与实际使用的模型数成正比，而非与支持的模型数成正比。

**负面与缓解**：

| 负面影响 | 缓解措施 |
| --- | --- |
| 首次请求慢（冷启动含模型加载） | 部署手册说明可用一次预热请求；PE-01 的口径明确排除首次加载 |
| 长时间运行后缓存累积占满显存 | 提供 `DELETE /models` 主动清理；运维手册给出监控与清理建议 |
| 单进程崩溃则服务整体不可用 | 容器重启策略；本期无高可用要求 |
| 缓存键设计错误会造成静默错误 | R-10 规则 + 两条回归测试（配置隔离、自动/预测模式分别缓存）常驻 CI |

## 验证方式

| 验证点 | 方式 |
| --- | --- |
| 相同配置复用同一实例 | 单元测试断言两次获取返回同一对象 |
| 不同配置分别缓存不互相覆盖 | 单元测试用两组配置交替请求，断言实例不同且各自正确 |
| 构造参数顺序无关 | 单元测试对同一组参数以不同顺序传入，断言命中同一缓存 |
| 非法构造参数返回 400 而非 500 | 错误分支测试；REL-02 |
| 依赖缺失给出 extras 提示 | 卸载 extras 后逐模型类型调用；REL-01 |

## 教学备注

这条决策里真正值钱的不是"选了方案 C"，而是**识别出"缓存键设计错误会导致静默错误"这个风险，并把它转化成一条宪章规则加两条常驻测试**。功能性 bug 会被用例抓住，静默错误不会——它需要你在设计阶段就预判到，然后专门布防。ADR 的作用就是把这种预判留在纸上，让三个月后的人知道那两条看起来"多余"的测试为什么不能删。
