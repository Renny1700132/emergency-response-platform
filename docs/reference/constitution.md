# constitution.md —— “澜图”项目宪章

> 版本 V1.0 · 第 3 关工程基线日冻结 · 通关实训第 3 组（教学样例）
> 本文件是 **AI 与人共同遵守的硬规则**。每次 AI 编码会话的启动仪式：读本文件 → 读当前任务卡 → 读相关 spec/契约片段 → 开始工作。
> 编写原则：**只写可机械检查的规则**（"SQL 禁拼接"可检查，"代码要优雅"不可检查）；**每条给反例**；**总数不超过 20 条**——规则太多等于没有规则。

---

## 一、技术栈白名单（R-01 ~ R-03）

**R-01 依赖白名单**
只允许使用《概要设计说明书》3.2 节选型表内的依赖。表外组件一律先提 ADR 再引入。

- 白名单：`lantu`（含 samgeo / samgeo2 / samgeo3 / text_sam extras）、`fastapi`、`uvicorn`、`click`、`prompt_toolkit`、`rasterio`、`geopandas`、`shapely`、`pyproj`、`numpy`、`pillow`、`pytest`、`pytest-cov`。
- 反例：为了做一个进度条引入 `rich`；为了读一个 JSON 引入 `pydantic-settings`。
- 检查方式：CI 比对 `requirements.lock` 与白名单，新增项未附 ADR 编号即失败。

**R-02 Python 版本下限**
代码必须在 Python 3.10 / 3.11 / 3.12 三个版本下均可运行（对应 MTN-03 的九组合 CI）。

- 反例：使用 3.12 才有的 `itertools.batched`；使用 3.11 才有的 `typing.Self` 而不加 `typing_extensions` 回退。
- 检查方式：三平台 × 三版本 CI 矩阵。

**R-03 上游边界**
不修改 `samgeo/` 上游包内的代码。需要的能力若上游没有，在本项目侧封装；确有上游缺陷，提 issue 并在本项目做临时适配层，适配层必须带 `# UPSTREAM-WORKAROUND:` 注释与 issue 链接。

- 反例：直接改 `samgeo/common.py` 里的函数签名让自己的调用能过。
- 检查方式：CI 对 `samgeo/` 目录做只读校验（diff 非空即失败）。

## 二、编码规范（R-04 ~ R-09）

**R-04 异常必须带上下文**
所有对外抛出的异常携带可定位信息：操作名、输入标识、失败原因。REST 层统一转换为结构化错误响应。

- 反例：`raise ValueError("invalid")`。
- 正例：`raise ValueError(f"raster_info: 无法读取 {path}，rasterio 报告 {exc}")`。
- 检查方式：静态检查规则 R-04，禁止无参数或单词级异常消息。

**R-05 HTTP 码合法、业务码在响应体**
HTTP 状态码只用标准语义（400 参数错误 / 404 资源不存在 / 409 状态冲突 / 413 体积超限 / 422 校验失败 / 500 未预期）。业务错误码放在响应体 `code` 字段，不占用 HTTP 码空间。

- 反例：参数错误返回 200 且 body 里写 `{"error": ...}`；自定义 HTTP 码 460。
- 检查方式：契约测试逐端点校验错误分支的状态码。

**R-06 路径与文件操作必须防穿越**
一切来自外部输入的路径先归一化并校验落在允许目录内；上传文件写入隔离临时目录，请求结束后清理（含异常路径）。

- 反例：`open(os.path.join(base, user_input))` 而不校验 `..`。
- 检查方式：静态检查 + SEC-01 渗透用例。

**R-07 数值不得凭空写入**
任何容量、耗时、精度数值，未经实测不得写入代码常量、配置或文档。估算值必须标注 `【估算，待实测】` 并登记待办。

- 反例：AI 说"模型约占 1.5 GB 显存"就写进 `docker-compose` 的内存上限。
- 检查方式：文档审计 + 代码评审自查清单；本条由《AI 翻车记录》第 2 条转化而来。

**R-08 公共函数必须有 docstring 与类型契约**
所有 `core/` 与 API 层的公共函数写 Google 风格 docstring，说明参数、返回值与抛出的异常。

- 反例：`def export_masks(project, output, fmt="geotiff"): ...` 无说明。
- 检查方式：`ruff` 的 docstring 规则 + 评审清单。

**R-09 禁止裸 `except`**
不允许 `except:` 或 `except Exception: pass`。必须捕获具体异常类型，或捕获后记录并重新抛出。

- 反例：`try: ... except: return None`。
- 检查方式：静态检查规则 R-09。

## 三、设计约束（R-10 ~ R-13）

**R-10 模型加载走缓存，配置不同不得互相覆盖**
模型实例按「模型版本 + 模型 ID + 冻结后的构造参数」为键缓存；不同配置分别缓存。

- 反例：用单个全局变量 `_model` 缓存，第二次不同配置的请求拿到上一次的实例。
- 检查方式：`tests/test_api.py::test_get_model_caches_distinct_configs_separately`。

**R-11 状态变更必须进历史与撤销栈**
对项目状态的每次实质性修改，都要追加历史条目并压入撤销栈，不允许直接改字典。

- 反例：`project["masks"] = path` 直接赋值。
- 正例：走 `set_masks()` / `session.mutate()`。
- 检查方式：静态检查禁止在 `core/` 之外对 project 字典下标赋值。

**R-12 可选依赖缺失是可预期状态，不是崩溃**
调用需要 extras 的模型前先检查可用性，不可用时返回准确安装命令。

- 反例：直接 `import sam2` 让 `ImportError` 冒泡到用户。
- 检查方式：REL-01 用例，卸载 extras 后逐类型调用。

**R-13 CLI 输出必须支持 `--json`**
每条子命令都要有机器可读输出模式，字段名稳定，不把人类可读的表格当作接口。

- 反例：只打印对齐表格，让调用方去正则解析。
- 检查方式：`tests/test_full_e2e.py::TestCLISubprocess` 逐命令校验 JSON 可解析。

## 四、测试与门禁（R-14 ~ R-17）

**R-14 测试先行**
核心逻辑的测试与实现同 PR，且**先红后绿**——先提交失败的用例，再提交实现。同 PR 同推的须在 PR 描述说明理由。

- 反例：实现合并两天后再补测试。
- 检查方式：PR 自查清单 + CI 首跑失败截图。

**R-15 覆盖率门禁**
核心模块单测覆盖率 ≥70%，增量代码覆盖率不低于存量均值。不达标 CI 阻断合并。

- 反例：为凑覆盖率写只调用不断言的"空测试"。
- 检查方式：`pytest-cov` 报告 + 评审人抽查断言密度。

**R-16 契约变更必须先改契约**
修改 REST 接口，顺序是：改 OpenAPI 契约 → 契约测试转红 → 改实现转绿。不允许实现先行、契约后补。

- 反例：先改 `api.py` 的响应结构，契约快照第二天才更新。
- 检查方式：契约测试对比归档快照。

**R-17 无需求来源的代码不写（镀金禁令）**
每个函数都要能指认它服务于哪条 FR。RTM 里没有来源的功能一律不开发。

- 反例：AI 顺手生成了 `/segmentation/interactive/redo` 端点，而契约中没有这个端点。
- 检查方式：PR 自查清单逐函数指认 FR 编号；评审人拦截。

## 五、AI 协作纪律（R-18 ~ R-20）

**R-18 一事一会话**
每个原子任务开新对话，不在长对话尾部续做新任务。会话开始加载本文件 + 任务卡 + 相关 spec 片段。

- 反例：在同一个对话里连续实现 T-15、T-16、T-17，上下文漂移导致改错文件。
- 检查方式：Prompt 日志按任务号归档，一任务一文件。

**R-19 先要计划，再要代码**
向 AI 提出编码任务时，先索取"实现步骤与文件清单"，人工确认后再生成代码。

- 反例：直接说"实现交互分割"然后接受 300 行输出。
- 检查方式：Prompt 日志中每个编码任务须有计划确认环节。

**R-20 AI 产出一律过人工审查并留痕**
每个含 AI 生成代码的 PR，必须在描述中声明 AI 参与范围、采纳率，并列出人工修改点。健康采纳率区间 40%~75%，长期高于 75% 说明审查不足，低于 40% 说明提示词质量差。

- 反例：PR 描述写"AI 辅助生成"，无任何审查记录。
- 检查方式：AI 使用审计抽查 PR 与 Prompt 日志对应关系。
