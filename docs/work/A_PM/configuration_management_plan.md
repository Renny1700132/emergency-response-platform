## 1 目的、范围与依据

### 1.1 目的

本计划规定项目配置项识别、版本、基线、变更、权限、审计、发布、回滚、配置库与归档规则，使需求、设计、接口、代码、数据迁移、测试、正式文档和过程证据保持可识别、可追踪、可恢复。本文建立管理规则，不表示任何未实施功能、外部联调、测试或验收已经通过。

### 1.2 适用范围

本计划适用于第三关设计与计划成果及后续经明确启动的实施、测试和交付活动。原型的 localStorage、Mock 数据和 prototypeStore 仅为走查参考，不作为正式配置、数据库、接口契约或验收证据。冻结需求仍为 39 条 FR、34 条★和 117 条 AC；本计划不得改变这些内容及关键数字、责任边界或既有 Issue 状态。

### 1.3 依据与优先级

| 依据 | 配置管理用途 |
|---|---|
| 当前用户指令、AGENTS.md、constitution | 任务边界、主责复核、同步、冻结与变更纪律 |
| BASELINE-G2-M2-R1.0、spec、RTM | 需求、AC、追踪和开放边界的受控输入 |
| plan.md、tasks.md | G3 工作包、责任、状态和 M3 门禁 |
| control/change_log.md、control/issues.md | 基线版本、Change、阻断与关闭证据 |
| governance/git_workflow.md、ai_logging.md | 仓库同步、最小暂存、非 force 推送和过程留痕 |

发生冲突时执行项目来源优先级；未知事实标记 `【待人工确认】`。冻结后不原位覆盖，必须通过 Change/CR 形成新版本。

## 2 组织、职责与职责分离

| 角色 | 配置管理职责 | 权限边界 |
|---|---|---|
| A 项目负责人 / 配置负责人 | 维护本计划、组织基线候选、召集 CCB、核对发布与回滚包 | 不得单方批准改变冻结需求、★、责任或验收强度 |
| B 技术负责人 | 评估代码、接口、数据迁移、部署和技术回滚影响 | 不替代 C 的符合性审查或有权业务裁决 |
| C 需求与质量负责人 | 复核需求/AC/★/数字一致性、配置审计与证据完整性；G3-13 唯一 Review 人 | 不代替 A 维护正式配置计划，不把自检冒充批准 |
| CCB | 对需裁决的 CR 作批准、驳回、延期或退回补充证据决定 | 成员为 A、B、C；涉及真实项目事实变化时还须取得有权书面裁决 |
| 配置项主责 | 修改获批范围、提交验证证据并同步受影响项 | 只能修改本人主责配置项；冻结项不得直接覆盖 |

提出、评估、批准、实施与验证应尽量职责分离。修订人不得代替指定 Review 人关闭评审问题；自动检查不得冒充人工签认。

## 3 配置项识别、登记与状态

### 3.1 配置项类别与清单

| CI 类别 | 代表性配置项 | 唯一标识 / 版本 | 主责 / 复核 | 最低完整性检查 |
|---|---|---|---|---|
| 需求与追踪 | SRS、spec、RTM、澄清、需求确认书 | 文档路径 + 版本/commit | A/B/C 依任务表 | 39 FR、34★、117 AC 与追踪差集 |
| 设计与决策 | HLD、DLD、DBD、接口说明、ADR/NFR | 文档编号 + 版本 + 设计 ID | 对应 G3 主责 / 指定复核 | FR/AC、设计 ID、状态和开放项 |
| 接口契约 | OpenAPI、错误语义、外部端口资料 | 文件名主版本 + commit | B / A、C | 可解析、版本、鉴权、错误、traceId、外部证据边界 |
| 数据库变更 | schema、迁移脚本、回滚脚本、种子/字典 | 顺序迁移号 + commit | B / 指定复核 | 前滚/回滚配对、依赖与不可逆风险 |
| 源码与构建 | 源码、依赖锁、构建脚本、镜像定义 | commit + release tag + 制品摘要 | B / 代码 Review 人 | 构建可重复、依赖锁定、扫描与测试证据 |
| 环境与部署 | 环境清单、参数模板、部署/恢复脚本 | 环境名 + 版本；密钥仅引用 | B / A | 配置与代码分离、敏感值不入库、恢复路径 |
| 测试资产 | 测试计划、用例、数据、脚本、报告、缺陷 | TC/AC ID + 执行版本 | C / 指定复核 | AC 回指、环境、数据、结果与原始证据 |
| 正式文档与图源 | DOCX、YAML、MD、PPTX/SVG/PNG 图源 | 文档编号 + V主.次 | 唯一主责 / 指定复核 | Reference、修订记录、编号引用、全页 QA |
| 治理与过程证据 | tasks、plan、constitution、Issue、Change、Prompt/Review | 路径 + commit + 时间 | 对应主责 / 复核 | 状态合法、事件真实、不可删除或伪造 |
| 基线与发布包 | baseline 清单、tag、manifest、校验值、发布/回滚记录 | BASELINE/REL ID + 版本 | A / C，技术项 B 复核 | 内容、依赖、审批、开放项、摘要与恢复验证 |

每个 CI 登记至少包含：CI-ID、名称、路径、类别、主责、复核人、当前版本、状态、上游依赖、关联 FR/AC/Issue/CR、最近 commit/tag、校验值（适用时）和保存位置。敏感信息只登记引用和保管责任，不写入 Git 或正式文档。

### 3.2 配置项状态

配置项状态采用 `WORKING → REVIEW → BASELINED → SUPERSEDED / ARCHIVED`。门禁失败进入 `BLOCKED` 并关联 Issue；被新版本替代的配置项保留历史，不删除、不回写为新内容。`tasks.md` 的任务状态独立采用 `TODO / DOING / REVIEW / DONE / BLOCKED`，不得把说明文字混入状态单元格。

## 4 版本、分支、提交与制品规则

### 4.1 版本标识

| 对象 | 规则 | 升级条件 |
|---|---|---|
| 正式文档 | `V主.次`；评审候选从 V0.1 起 | 冻结范围/结构或批准基线变化升主版本；受控修订升次版本 |
| API | URI/契约主版本 + 文件版本 | 破坏性变更升主版本；兼容扩展按批准策略升级 |
| 应用发布 | `v主.次.修订` | 不兼容变化 / 兼容功能 / 缺陷修复分别升级 |
| 数据迁移 | 单调递增且唯一的迁移号 | 每次 schema/data migration 新增编号，禁止改写已执行迁移 |
| 基线 | `BASELINE-阶段-版本` | 每次批准冻结生成新 ID，不覆盖旧基线 |
| CR | `CR-YYYY-NNN` | 每项变更申请唯一编号，撤销后编号不复用 |

### 4.2 Git 与提交

共享仓库使用 `master` 受控历史。正式任务开始和结束必须安全 fetch/pull，最小暂存，使用可追踪提交说明，普通非 force 推送；禁止改写共享历史、强推、提交凭据或把过程证据加入忽略规则。并发变更先核对范围，语义冲突停止并请求裁决。发布 tag 只指向已通过对应门禁的不可变 commit。

### 4.3 制品完整性

发布包应记录源 commit、tag、构建环境、依赖锁、制品文件名、SHA-256、数据库迁移范围、配置模板版本、测试/扫描证据及回滚包。相同 tag 不得对应不同字节；如需修正，发布新版本。

## 5 基线建立、冻结与解除

### 5.1 基线类型与内容

| 基线 | 典型内容 | 建立门禁 | 变更权限 |
|---|---|---|---|
| 需求基线 | SRS、spec、RTM、澄清、确认书 | 编号/追踪/★/数字一致，Review 通过 | CR + CCB；事实变化另需有权书面裁决 |
| 设计基线 | HLD、DLD、DBD、接口、OpenAPI、ADR/NFR | 统一 DoD、Review 闭环、开放阻断已关闭或获裁决 | CR + CCB |
| 测试基线 | 计划、用例、数据、脚本、环境清单 | AC 追踪、预期、准入/准出和证据字段齐全 | CR + CCB |
| 发布基线 | 源码 tag、迁移、配置、制品、文档、测试报告 | 构建/测试/安全/恢复门禁通过 | CCB + 发布批准人【待人工确认】 |
| 归档基线 | 最终交付物、签认、校验清单、操作与恢复资料 | 交付清单一致、校验通过、保存责任明确 | 只读；变更生成新归档版本 |

### 5.2 冻结步骤

1. 主责提交基线候选清单，列明 CI、版本、依赖、commit/tag、校验值、Review、Issue/CR 和开放项。
2. A 执行跨项一致性和状态检查；B 检查适用技术项；C 检查需求、★、数字、责任与证据符合性。
3. 阻断项未关闭或未取得有权裁决时，记录 `DO_NOT_FREEZE`，不得创建 FROZEN 基线。
4. 获批后创建不可变 tag/快照，更新 change log、CI 状态与基线清单，通知相关人员。
5. 冻结后发现问题必须提出新 CR，形成新版本；禁止原位修补历史基线。

当前 `ISSUE-G3-01-001` 和 `ISSUE-G3-10-001` 保持 OPEN；本计划不关闭它们，也不授权 M3 冻结。

## 6 变更、CR 与 CCB 流程

### 6.1 CR 最小字段

CR 必须包含：编号、提出人/时间、变更对象与原因、来源、现状/目标、受影响 CI、FR/AC/★/关键数字、接口/数据/安全/进度/成本/质量/测试/文档/培训影响、兼容与回滚方案、风险、实施人、验证人、拟发布版本、裁决和通知范围。信息不足时退回补充，不得先实施后补单。

### 6.2 流程与裁决

| 步骤 | 责任与活动 | 输出 / 门禁 |
|---|---|---|
| 1 提出与登记 | 提出人提交 CR，配置负责人赋唯一编号 | CR 状态 `SUBMITTED`；范围可定位 |
| 2 分诊 | A/C 判断勘误、一般、重大或紧急；检查是否触及冻结事实 | 分类、优先级、所需裁决人 |
| 3 影响分析 | A 组织，B 分析技术/回滚，C 分析需求/合规/追踪 | 受影响 CI、RTM、测试、发布和风险清单 |
| 4 CCB 裁决 | A/B/C 作批准、驳回、延期或补证决定 | 书面决定；事实变化须有权裁决后方可批准 |
| 5 实施 | 主责仅修改批准范围，同步全部受影响 CI | commit/版本、迁移与回滚包、修订记录 |
| 6 验证与复核 | 非修订人按批准条件验证；C 核对追踪与证据 | 测试/审计/Review 证据；失败退回 |
| 7 发布与归档 | A 核对版本和门禁，创建新 tag/基线并通知 | 发布/基线记录、CR `CLOSED`、旧版保留 |

重大变更包括影响冻结 FR、★、AC、关键数字、范围、责任、验收强度、外部契约主版本、不可逆数据迁移或里程碑的事项。紧急修复可走加急评估，但不得绕过授权、审计、验证和事后 CCB 确认。

## 7 权限、安全与配置审计

### 7.1 权限控制

配置库按最小权限和职责分离授权：工作区允许主责修改；Review 人可审查和提出意见；受保护分支、tag、基线与归档仅由授权角色操作。账号使用实名、独立凭据和多因素认证（平台支持时）；权限新增、变更、撤销均留痕，人员或职责变化时及时回收。密钥、口令、证书私钥和生产敏感配置不得进入 Git，只保存于甲方认可的秘密管理设施【待人工确认】。

### 7.2 审计类型

| 审计 | 检查内容 | 时点 | 证据 |
|---|---|---|---|
| 配置状态审计 | CI 版本、状态、主责、依赖、CR/Issue 与仓库一致 | 每周及里程碑前 | 配置状态报告、差异清单 |
| 功能配置审计 FCA | 基线内容是否覆盖批准需求与 AC | 基线候选、发布候选 | RTM、测试/Review、偏差记录 |
| 物理配置审计 PCA | 清单中的文件、制品、图源、迁移、校验值是否齐全 | 冻结/发布/归档前 | manifest、SHA-256、仓库/tag 快照 |
| 权限审计 | 分支、tag、基线、归档和敏感配置访问是否最小化 | 每月及人员变化后 | 权限清单、变更记录、异常处置 |

审计发现按 Issue/不符合流程登记；未闭环 BLOCKER 不得冻结或发布。审计日志和 Review/Prompt 证据不得删除、回写或伪造。

## 8 发布、部署与回滚

### 8.1 发布准入

发布候选必须具备：批准 CR/范围、唯一版本和 tag、可重复构建、依赖与安全检查、受影响测试、迁移/备份/恢复验证、配置差异、正式文档、已知问题、监控与通知安排。真实环境、账号、窗口或外部接口尚未确认时标记 `BLOCKED/PENDING`，不得用 Mock 结论替代。

### 8.2 发布与回滚步骤

1. 发布前生成 manifest 和校验值，备份数据及现行配置，确认维护窗口与责任人【待人工确认】。
2. 按受控顺序部署配置、迁移和应用，记录操作者、时间、版本、环境、结果与 trace/日志引用。
3. 执行健康检查和批准的冒烟/回归测试；失败立即停止扩散并按回滚判据处置。
4. 回滚优先恢复上一已知良好应用/配置版本；数据回滚仅使用已验证脚本或恢复点。不可逆迁移必须在发布前给出前向修复方案并获 CCB 接受风险。
5. 回滚后复核数据一致性、接口兼容和审计记录，登记 Issue/CR，禁止复用失败版本号。

回滚触发包括：BLOCKER/严重安全问题、核心 AC 失败、迁移不可接受错误、关键接口持续失败且无批准降级、完整性校验不一致或监控超过批准阈值。具体生产阈值和维护窗口由后续受控发布计划确认。

## 10 AC-G2-FR-013-01 配置抽查

`AC-G2-FR-013-01` 的受控语义是：授权用户在 Web 或 H5 端提交事件基本信息时，系统创建事件并生成可追踪编号。本计划不把该 AC 改写成配置管理需求，而是规定支撑其实现和验证的配置链必须完整。

| 抽查对象 | 必须一致的配置证据 | 判定 |
|---|---|---|
| 需求与追踪 | spec、SRS、RTM 中 AC 标识和语义一致 | 不一致即阻断相关基线 |
| 设计与数据 | DLD-TR-013、DBD-TR-013 回指 AC，事件编号唯一与审计字段可定位 | 缺设计/数据落点不准出 |
| 接口契约 | API-TR-013 与 OpenAPI 操作保留 AC 引用、鉴权、错误和 traceId | 契约漂移须走 CR |
| 测试资产 | TC-G2-FR-013-01 与执行版本、环境、数据、预期和原始证据绑定 | 未执行不得写 PASS |
| 发布包 | commit/tag、迁移、配置、制品和回滚包能回指同一批准版本 | 版本不一致不得发布 |

主责自检仅检查上述设计链和配置规则已建立，不声称事件功能、Web/H5、接口或测试已经执行通过。

## 11 配置状态报告、例外与本计划准出

配置状态报告至少列出：CI 总数与状态、最近版本、基线/tag、待审 CR、开放 Issue、配置差异、审计发现、发布/回滚、权限变化、备份/恢复抽检以及责任人和下一步。例外必须有范围、原因、风险、期限、责任人、补救和有权批准；到期未关闭自动升级 Issue，不能永久口头豁免。

G3-13 主责准出检查：配置项识别、版本、基线、CR/CCB、权限与审计、发布与回滚、配置库与归档章节齐全；AC-G2-FR-013-01 未被改义且追踪链可抽查；Reference 24 已物理继承；编号/引用、工作稿镜像、案例隔离、全页渲染和无障碍检查通过。主责自检后任务进入 REVIEW，等待 C 独立复核；未取得 C Review 前不得置 DONE。
