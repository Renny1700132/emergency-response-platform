## 1 引言

### 1.1 编写目的

本说明书把需求级实体和概要设计中的数据边界落实为概念、逻辑和物理三级数据库设计候选，供详细设计、接口设计、实现、迁移、测试和运维使用。文档给出数据主责、实体关系、表结构、键与约束、索引、事务、审计、容量、保存、备份和演进规则，同时明确尚待接口联调或人工决策的内容。

本稿不把未发生的联调、压测、恢复演练或甲方验收写成已通过。数据库产品、部署拓扑、地图坐标系和外部接口字段尚未完成 ADR 或现场确认，因此物理设计采用可移植关系模型；厂商专有类型、分区语法和空间扩展均保留为后续决策项。

### 1.2 范围和非目标

本项目保存应急业务事实、状态变化、外部关联、消息回执、审计和可重建读模型。录像文件由既有视频系统保存不少于 30 天，本项目仅保存受控视频引用和调阅结果；附件实体文件由统一中台文件能力保存，本项目仅保存文件标识、版本、权限和业务引用；身份、组织和权限主数据由统一中台维护，本项目保存必要的外部标识、业务快照和关联，不复制建设通用主数据平台。

### 1.3 设计状态和约束

G3-03 已完成 C 最终复核并置为 DONE，本文按其已准出版本中的单一写入主责、端口隔离和可重建态势投影设计；后续如架构边界发生变化，应通过变更单评估本稿。`ISSUE-G3-01-001` 仍为 OPEN，视频与统一消息的真实字段、认证、回执和性能证据不得冻结；本文只定义内部关联字段与可扩展映射边界。

## 2 数据设计原则与资产总览

### 2.1 设计原则

1. **领域单一写入。** 预案、事件、任务、资源、值班、演练和知识对象分别由其主责模块写入，跨模块通过受控服务和事件协作。
2. **标识分离。** 数据库主键、业务编号、外部系统标识、幂等键分别建模，不复用一个字段承担多种语义。
3. **时间可追溯。** 至少区分业务发生时间、源系统产生时间、本系统接收时间和处理时间；迟到数据追加记录，不覆盖历史。
4. **事实与投影分离。** 事件、任务、回执和盘点记录是事实源；态势、统计和看板表均可由事实重建，不允许反向修改事实。
5. **状态显式。** 状态迁移通过合法路径、版本号或乐观锁控制；历史责任人、原截止时间和原版本均保留。
6. **外部能力引用。** 文件、视频、身份、组织、消息和工作流采用外部引用或调用记录，不在本库重复保存外部系统的完整主数据或二进制内容。
7. **待验证不固化。** 未经 ADR、现场资料或实测确认的数据库产品、坐标类型、分区阈值、字段长度和容量参数保持候选状态。

## 3 概念数据模型

### 3.1 核心数据域关系

[[FIGURE:core_domain_model]]

预案以版本为发布单位，预案版本包含流程节点和任务模板。经核实的事件选择一个有效预案版本启动后生成处置任务，因此事件必须保存启动时的预案版本标识，任务必须保存模板快照或模板版本标识。事件拥有续报、时间线和关闭材料；处置任务拥有指派历史、反馈和消息投递记录。

人员与组织来自统一中台，系统保存人员外部标识以及事件、任务和值班发生时的职责快照。位置快照属于人员在某一源时间的观测，不属于人员主档。物资站点拥有物资台账；盘点计划发布时固化库存快照，实盘记录与期间出入库分开保存，复核后生成调整记录。

演练计划可产生多次执行，补演执行通过原计划或原执行标识关联，整改项的关闭不删除原逾期事实。消息投递、外部调用、附件引用和审计日志通过业务对象类型与对象标识关联，但不能替代领域事实。

### 3.2 关键关系和基数

| 关系 | 基数 | 约束 |
| --- | --- | --- |
| 预案—预案版本 | 1:N | 已发布版本不可原位修改，新修订产生新版本 |
| 预案版本—任务模板 | 1:N | 模板顺序、责任、时限和依赖随版本冻结 |
| 事件—预案版本 | N:0..1 | 未启动预案的事件允许为空；启动后保存确定版本 |
| 事件—续报 | 1:N | 续报只追加；四类时间完整保存 |
| 事件—处置任务 | 1:N | 每个任务只归属一个事件；可记录来源模板 |
| 任务—指派历史 | 1:N | 重指派追加历史，不覆盖原责任人和原因 |
| 任务—反馈/附件 | 1:N | 反馈只追加；附件使用受控引用 |
| 人员—位置快照 | 1:N | 位置按源时间排序，过期判定由配置控制 |
| 站点—物资台账 | 1:N | 业务键在有效范围内唯一 |
| 盘点计划—库存快照/实盘 | 1:N | 发布时形成快照，期间变动独立保留 |
| 值班计划—打卡记录 | 1:N | 二维码版本和有效期参与校验，重复扫码幂等 |
| 演练计划—演练执行 | 1:N | 补演关联原计划；取消/逾期历史保留 |
| 业务对象—消息投递/调用日志 | 1:N | 使用业务键、traceId 和幂等键关联 |

## 5 物理数据库设计

### 5.1 数据库产品与命名

采用关系型数据库作为物理实现候选，具体 DBMS、版本、高可用形态和厂商专有扩展须由 G3-07 ADR 与甲方环境确认后定案。表名和字段名使用小写 `snake_case`；主键、外键、唯一约束和检查约束均显式命名；生产库、测试库和开发库隔离，凭据通过部署环境或密钥能力注入。

空间数据当前采用坐标参考、楼层、X/Y、经纬度和源精度等普通字段表达，以保证未确认坐标系时不固化错误空间类型。坐标系与楼层映射确认后，才可通过变更评估引入厂商空间类型或空间索引。

### 5.2 逻辑类型到物理类型映射

| 逻辑类型 | 可移植物理类型候选 | 约束 |
| --- | --- | --- |
| 标识 | UUID 或 BIGINT | 全库统一，不混用；由 ADR 确定生成方式 |
| 业务编号/外部标识 | VARCHAR(n) | `n` 由真实数据画像确定，禁止凭空固定 |
| 枚举状态 | VARCHAR + CHECK / 字典表 | 状态集合小且稳定用 CHECK；需配置时用字典表 |
| 数量 | DECIMAL(p,s) | 精度由物资计量单位确认，不使用浮点保存账务数量 |
| 时间 | TIMESTAMP WITH TIME ZONE 或等价类型 | 库内统一时区策略，展示层按业务时区转换 |
| 长文本 | TEXT / CLOB | 设置接口和页面长度门禁，避免无界输入 |
| 扩展载荷 | JSON / TEXT | 仅保存版本化、受控扩展；核心查询字段必须独立列化 |
| 布尔 | BOOLEAN / SMALLINT | 统一取值约束 |

### 5.3 主键、外键和删除策略

业务事实表使用不可变主键。外键在同一数据库边界内启用；外部系统对象使用 `source_system + external_id` 组合唯一，不建立跨库物理外键。预案版本、事件、任务、盘点快照、出入库、打卡、消息尝试和审计等历史事实禁止级联删除。配置对象可停用；允许删除的附件引用采用逻辑删除并记录删除人、时间和原因。

### 5.4 索引设计

| 索引 ID | 表与列 | 用途 | 类型/状态 |
| --- | --- | --- | --- |
| IDX-INC-01 | `em_incident(status, occurred_at)` | 待办与时间线检索 | 普通复合索引 |
| IDX-INC-02 | `em_incident(source_system, external_alert_id)` | 可靠外部告警去重 | 条件唯一；空值语义待 DBMS 确认 |
| IDX-UPD-01 | `em_incident_update(incident_id, occurred_at, received_at)` | 事件时间线与迟到数据排序 | 复合索引 |
| IDX-TASK-01 | `em_response_task(incident_id, status, deadline_at)` | 事件任务和超期扫描 | 复合索引 |
| IDX-TASK-02 | `em_response_task(assignee_id, status, deadline_at)` | 个人待办 | 复合索引 |
| IDX-POS-01 | `em_position_snapshot(person_id, source_time desc)` | 最近有效位置 | 复合索引；新鲜度仍按配置判断 |
| IDX-STOCK-01 | `em_stock_movement(site_id, item_id, occurred_at)` | 期间变动核算 | 复合索引 |
| IDX-INV-01 | `em_inventory_record(plan_id, site_id, item_id)` | 盘点差异 | 复合索引 |
| IDX-ATT-01 | `em_attendance_record(person_id, task_id, check_point_id, scanned_at)` | 打卡核验 | 复合索引；另设幂等唯一键 |
| IDX-MSG-01 | `em_message_delivery(status, next_retry_at)` | 重试任务扫描 | 复合索引 |
| IDX-CALL-01 | `em_external_call_log(trace_id, requested_at)` | 联调与故障定位 | 复合索引 |
| IDX-AUD-01 | `em_audit_log(object_type, object_id, occurred_at)` | 对象审计追踪 | 复合索引 |

索引是否覆盖、顺序是否调整、是否分区均须以真实查询计划和压测数据判断。不得仅因预计数据量提前建立大量冗余索引。

### 5.5 事务与并发

1. 事件创建、状态迁移、任务创建和同事务 Outbox 写入必须原子提交。
2. 任务重指派在同一事务内写入当前责任人和指派历史，使用 `version_no` 防止覆盖并发更新。
3. 盘点发布在一致性读边界内生成库存快照；期间出入库独立提交，复核计算同时读取快照、变动与实盘。
4. 打卡、外部告警和回执先校验幂等键；并发重复请求返回首个已受理结果或一致状态。
5. 门禁等控制动作只记录一次授权下发与回执，不由通用重试任务自动重放。

## 6 完整性、一致性与安全策略

### 6.1 数据完整性

非空、唯一、范围、枚举和引用完整性优先由数据库约束保障；涉及跨领域业务语义的规则由领域服务校验并写审计。类型停用不能破坏历史引用；关闭事件、完成任务、发布预案、确认盘点等敏感操作均需权限和状态前置条件。

### 6.2 十项澄清的数据落点

| 澄清 | 数据设计落点 | 验证证据 |
| --- | --- | --- |
| G2-RCLR-001 | 外部告警组合唯一键、续报追加、人工关联入口 | 重复可靠 ID 不产生第二事件；无 ID 不误合并 |
| G2-RCLR-002 | 核实截止时间、超时状态、升级记录 | 超时后仍待核实，不自动启动预案 |
| G2-RCLR-003 | 指派历史与截止时间变更审计 | 重指派前后责任人和期限可还原 |
| G2-RCLR-004 | 四类时间和迟到标记 | 迟到数据追加且时间线顺序可解释 |
| G2-RCLR-005 | 二维码版本/有效期、打卡幂等唯一键 | 过期拒绝、重复扫码仅一条有效记录 |
| G2-RCLR-006 | 发布快照、期间变动、实盘和调整分表 | 三类数量同屏核对且可追溯 |
| G2-RCLR-007 | 原计划、补演和实际完成分离 | 补演不删除逾期/取消历史 |
| G2-RCLR-008 | 消息、发送尝试和回执关联 | 迟到/重复回执不重复计数或触发动作 |
| G2-RCLR-009 | 位置源时间、新鲜度状态和最后有效值 | 过期位置不参与自动邻近调派 |
| G2-RCLR-010 | 附件引用逻辑删除和保护标识 | 关闭/归档业务引用不可普通物理删除 |

### 6.3 安全与审计

数据访问继承统一中台身份、组织和权限上下文，并在业务服务层实施最小权限和数据范围校验。数据库账号按应用读写、只读查询、迁移和备份职责分离；凭据不得进入代码、制品、日志或数据库业务表。敏感字段、接口请求和日志按最小必要原则保存，手机号、证件等字段如实际出现须经人工确认其分类、脱敏和加密要求。

审计记录至少包含操作者、组织、动作、对象、结果、发生时间、traceId 和终端摘要。审计表追加写并限制普通业务账号更新/删除。正式的加密算法、密钥托管方式和审计归档介质待甲方安全环境确认。

## 7 容量、保存、备份和演进

### 7.1 容量基线

| 对象 | 受控数量或周期 | 设计处理 |
| --- | --- | --- |
| 预案 / 任务模板 | ≥50 / ≥200 | 普通关系表和版本索引即可，初始化数量由甲方数据决定 |
| 事件 / 任务 | 约 200 事件/年、10 任务/事件；在线 ≥10 年，至少 2 万事件、20 万任务 | 按状态与时间索引；是否按时间分区待真实数据和压测决定 |
| 人员 / 站点 / 台账 | ≥300 / ≥30 / ≥1000 | 外部标识唯一、站点物资复合唯一、版本并发控制 |
| 打卡 | 约 200 条/日、约 7.3 万条/年；在线 ≥3 年 | 三年约 21.9 万条为估算输入；按人员/任务/时间索引 |
| 过程数据 | ≥3 年 | 归档后仍需授权可查，具体冷热分层待环境确认 |
| 审计日志 | ≥180 天 | 在线查询索引和受控归档；不得提前删除 |
| 视频录像 | 既有系统保存 ≥30 天 | 本库不保存录像，只保存引用和调阅结果 |

上述数量用于设计边界，不等同于实际库容。行宽、附件引用数量、日志增长、索引放大和备份窗口必须通过样本数据画像与压测测量；KN-073/074 等建议值不得直接转化为生产配置。

### 7.2 保存与归档

事件和任务满足在线不少于 10 年；打卡在线不少于 3 年；过程数据不少于 3 年；审计不少于 180 天。达到保存期限并不自动授权删除，须由数据责任人、合规复核和甲方策略共同确认。归档必须保留主外键可解释关系、版本、校验摘要、归档批次和恢复验证记录。

### 7.3 备份与恢复

甲方提供服务器、网络、备份介质和后备电源，乙方提交数据库备份与恢复方案。建议形成全量与增量/日志备份组合、异地或隔离介质副本、定期恢复演练和备份校验，但具体周期、RPO 和保留份数尚无受控裁决，标记为【待人工确认】。恢复方案须支撑现有 MTTR 不超过 2 小时的要求并在目标环境演练，未演练前不得宣称满足。

### 7.4 初始化、迁移和演进

基础业务源数据由甲方提供并确认业务正确性；乙方负责模板、清洗映射、导入和技术校验，最终成果双方确认。迁移按“源数据盘点—字段映射—清洗规则—试导入—差异报告—确认—正式导入—校验”执行，每批记录来源、版本、数量、成功/失败和错误原因。

数据库变更使用单向、可重复检查的迁移脚本，禁止生产环境手工改表后不留记录。破坏性变更采用扩展—兼容—迁移—切换—清理步骤；状态枚举、外部 ID 和时间语义变更须先评估 RTM、接口与历史数据。态势投影允许清空重建，但事实表迁移不得依赖投影反推。
