# AI 翻车记录：最终门禁暴露的错误假设

## 记录 1：把既有依赖版本视为安全

- 现象：首次 `npm run quality` 在依赖安全阶段失败，报告 3 个高危漏洞。
- 根因：实现阶段沿用了旧锁文件，没有先验证当前公告状态；“此前审计为 0”被错误当成当前事实。
- 修复：Vue 升级至 3.5.43，并应用非强制锁文件安全修复；复跑根/前端审计均为 0 高危。
- 预防：最终准出必须实时执行依赖审计，历史报告只能作趋势证据。

## 记录 2：内存测试通过掩盖 PostgreSQL 参数错误

- 现象：真实 PostgreSQL 集成中事件列表返回 `42P18 could not determine data type of parameter $1`。
- 根因：计数 SQL 复用了从 `$3` 起的过滤条件，却传入未在 SQL 中使用的 `$1/$2`；内存适配测试无法暴露该错误。
- 修复：为 count 查询使用连续 `$1—$5` 参数并补充 HTTP 状态诊断断言；PostgreSQL 专项 2/2 通过，重启后保留 36 张 `em_*` 表、1 条已关闭事件和 14 条审计记录。
- 预防：涉及 SQL 的最终门禁必须包含真实 PostgreSQL、迁移 up/down/re-up、服务重建和数据库进程重启恢复，不能以 Mock/内存库替代。
