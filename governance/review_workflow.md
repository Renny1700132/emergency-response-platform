# 主责与评审工作流

## 唯一主责

- A 主责：项目建议书、项目计划 v1、风险登记册 v1、技术投标书整合、跨文档一致性、述标、最终冻结。
- B 主责：技术分析、架构、功能方案、关键技术、数据/接口、非功能设计、验证、技术风险输入和技术质询。
- C 主责：需求解析、facts、key_numbers、compliance_matrix、★检查、澄清、偏离检查、AI 日志/审计和最终符合性。

正式产物只存在一名主责人。协作者可以给出输入和 Review，但不得静默维护另一套版本。

## 默认复核关系

| 主责产物 | 默认复核人 | 复核重点 |
| --- | --- | --- |
| A | C | 需求符合性、数字与来源、★条款、提交物完整性 |
| B | A | 方案可交付性、跨章节一致性、表达与计划接口 |
| C | B | 技术理解、条款映射正确性、可验证性 |

## Issue 闭环

```text
Review / Issue
  ↓
在 control/issues.md 编号登记
  ↓
正式产物主责人修改
  ↓
复核人验证证据并关闭
```

复核人不得越过主责直接维护独立正式稿。紧急修正也必须留下 Issue、修改人和复核证据。

## 状态与准出

- `TODO`：未开始。
- `DOING`：主责正在处理。
- `REVIEW`：主责自检完成，等待复核。
- `DONE`：复核通过或任务定义明确允许自检关闭。
- `BLOCKED`：存在无法在当前权限/信息内解决的阻塞，必须说明原因和解除条件。

最终冻结前：C 完成符合性检查，B 完成技术正确性检查，A 完成跨文档一致性检查并执行冻结。任何 ★ 负偏离、来源不明关键数字或未关闭高影响 Issue 都禁止冻结。
