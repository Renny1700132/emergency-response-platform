## 2. Findings

### ISSUE-G4-03-001｜MAJOR｜模块—FR 追踪错配

`frontend/src/router/modules.ts:13-26` 把多个模块写成连续但错误的 FR 范围。例如 `MOD-TASK` 被写为 004—006，冻结映射实际为 003、015、020、022；`MOD-SITUATION` 被写为 017—020，实际为 004—007、026、039；`MOD-DUTY` 被写为 021—023，实际为 017—020、024、032；`MOD-KNOWLEDGE` 被写为 024—026，实际为 016、038。H5 路由也直接复用领域模块 ID，没有表达冻结的 `MOD-MOBILE` 接入边界。

影响：页面自报的需求范围会误导后续 G4-06/G4-09、RTM 和验收，且 `quality/selfcheck/G4-03.json` 的 traceability PASS 与事实不符。

最小修复：由 A 按冻结 §4.1 修正路由元数据；H5 同时保留 `MOD-MOBILE` 渠道边界和被调用领域模块，不静默改写冻结基线；增加自动测试逐项核对模块 ID/FR 集合，修正 selfcheck 后复跑质量门禁。

### ISSUE-G4-03-002｜MAJOR｜API Client 未形成操作级类型约束

`frontend/src/shared/http/api-client.ts:23-26` 的 `request(method: string, path: ApiPath)`、`get<TResponse>` 和 `post<TResponse,TBody>` 只校验 path 存在。调用方仍可对仅支持 POST 的路径发 GET、为无 body 的操作传 body，或把任意响应声明成任意 `TResponse`，TypeScript 不会依据 `paths[P][method]` 的 OpenAPI operation 拒绝。

影响：虽然生成了 `schema.d.ts`，但后续业务无法依赖编译器保证方法、参数、请求体和响应契约一致，不满足 G4-03“类型化 API Client、由冻结契约生成或核对”的核心 DoD。

最小修复：从生成的 `paths`/operations 推导 method-specific path、query/path/header、requestBody 和 success response 类型，或采用受控的 OpenAPI typed-fetch 客户端；至少添加 `tsc` 类型负例（错误方法/错误 body/错误响应必须编译失败）与正确调用正例。

### ISSUE-G4-03-003｜MAJOR｜Node 支持声明与测试工具链不兼容

根 `package.json:6-8` 与 `frontend/package.json:6-8` 声明 Node `>=20.19.0`；`frontend/package-lock.json:2133` 中 Vitest 5.0.1 声明 Node `^22.12.0 || ^24.0.0 || >=26.0.0`。本次门禁运行环境是 Node `v24.21.0`，不能证明声明允许的 Node 20 可用。

影响：按仓库公开 engine 使用 Node 20 的成员可能无法可靠安装或运行测试，质量门禁的可重复性不成立。

最小修复：二选一并统一根/frontend/README/锁文件：回退到支持 Node 20.19 的测试工具链，或把项目最低 Node 版本提升到实际支持值并明确获得团队环境确认；在受支持最低版本复跑 `npm ci` 和 `npm run quality`。
