# 最小可验证原型（Prototype）规划

## 1. 目标与边界

本目录用于第三关正式设计与开发前的 **Minimum Validation Prototype（最小验证原型）** 规划。原型的目标是把第二关的需求和规格转化为可走查的页面、状态与交互闭环，验证主要操作链是否自然，并为后续架构、数据、接口和测试设计提供直观输入。

它不是最终系统、第三关正式架构实现、真实联调系统、性能验证系统或完整业务系统。原型中的业务数据均为课程模拟数据；外部系统一律采用 Mock。Mock 演示结果不得描述为真实验收结果。

以下指标仅作为页面目标或状态展示，不在原型阶段宣称已经验证：预案启动通知/任务下发 ≤3 秒、告警接入 ≤2 秒、事件确认到任务下达 ≤3 分钟、消息并行/到达率、定位刷新/亚米级、视频首帧、Web/地图/扫码性能、≥100 在线用户、安全、可用率和部署时长等。原型不得改变 39 条 FR、34 条★、关键数字、责任边界或验收要求。

本阶段不连接真实视频、定位、门禁、IoT、统一消息、中台或地图服务；不建立正式后端、数据库、Redis、MQ、微服务、生产 Docker、真实 GB/T 28181、SSO/OAuth 或 CI/CD。

## 2. 原型级技术建议

后续开发可优先采用 Vue 3、Vite、Vue Router、Element Plus、ECharts；仅在跨页面状态确有必要时使用 Pinia。本地 Mock JSON/JS 用于数据和外部回执模拟，localStorage 仅用于少量演示状态持久化。

原型原则上只做前端。正式架构、接口协议、数据库模型和部署方式必须在第三关经设计与评审后确定；原型代码能否迁移届时再判断。本轮只建立本 README，**不创建** `src/`、`public/`、`package.json` 或任何代码目录。后续工程如获启动，建议保持：

```text
prototype/
├── src/        # views、components、router、mock、assets
├── public/
├── package.json
└── README.md
```

## 3. 页面与功能范围

11 个业务模块应在信息架构或菜单层面可见，但不为每条 FR 制作独立页面。Web 端优先规划：登录/角色切换、应急驾驶舱、应急预案、事件管理、指挥态势、应急任务、人员与值班、物资管理、演练管理、打卡管理、基础配置、数据统计、综合安防与系统对接状态。

H5 只保留移动事件上报、个人任务、任务确认/反馈、应急演练、扫码打卡和物资盘点。H5 应体现既有冻结边界：嵌入现有智慧管理 APP，不开发原生 Android/iOS APP。

## 4. 优先验证的业务闭环

按价值排序建设，而非追求覆盖全部 39 条 FR：

| 优先级 | 最小闭环 | 主要追踪 |
| --- | --- | --- |
| P1 | 事件上报 → 核实审批 → 启动预案 → 形成/下发任务 → H5 接收与反馈 → 指挥端查看 → 关闭 → 评估/调查/报告 | FR-01.*、FR-05.*、FR-08.1、FR-08.2 |
| P2 | 事件 → 指挥态势 → Mock 人员位置/视频/物资站点 → 时间线与任务状态 | FR-02.*、FR-10.1、FR-11.3 |
| P3 | 演练计划 → 演练任务 → H5 执行 → 结果提交 → 评估 | FR-04.*、FR-08.4 |
| P4 | 配置打卡点 → H5 模拟扫码 → 就位记录 → 统计 → 异常提醒 | FR-06.*、FR-08.5 |
| P5 | 物资台账 → 创建盘点 → H5 盘点 → 差异显示 → 复核更新库存 | FR-03.3、FR-03.4、FR-08.6 |

原型页面、Mock 数据说明或后续代码注释应保留对应 `FR-xx.x`，以便走查；不为原型单独建立庞大 RTM。非 MVP 的 FR-01.4、FR-03.1/03.2、FR-07.*、FR-08.3、FR-09.1 仍为本期正式范围，但不要求在本最小原型中形成复杂闭环。

## 5. Mock 与数据规则

所有外部依赖必须在页面显式标注“模拟连接 / Mock”或“待第三关后续集成验证”：地图用 SVG/平面图或静态占位；定位用固定或定时变化的模拟坐标；视频用静态画面/占位播放器；IoT 用模拟告警；门禁用“授权确认 → 请求 → 成功/失败”状态；消息用发送、回执、重试状态；中台用模拟用户、组织和权限；统计由本地 Mock 数据计算；H5 扫码通过按钮或模拟二维码触发，不调用硬件。

数据使用虚构人员、事件和场所名称，不使用敏感真实数据。时间统一 UTC+8，时间字段优先 ISO 8601；临时 ID 采用一致格式，如 `EVT-20260914-001`、`PLAN-FIRE-001`、`TASK-20260914-001`、`DRILL-202609-001`。这些临时结构不约束后续正式数据库设计。

## 6. UI 与状态表达

采用普通后台管理信息架构：左侧导航、顶栏和主内容区；蓝/灰为主色，红/橙仅表示告警、风险与紧急状态。首页以少量统计卡、事件列表和图表为主，避免复杂动画和“大屏炫技”。核心评价是用户能否理解系统状态并顺利完成闭环。

状态必须可见：待核实、待审批、处置中、待反馈、已关闭、Mock 失败/重试、数据过期或待人工处置等不能只靠颜色表达。定位、视频、门禁、消息与中台的 Mock 状态不得被误认为真实联通或真实验收。

## 7. 完成定义与停止规则

后续原型达到以下程度即可停止扩张并进入第三关正式设计：

1. 本地可启动，主要 Web 菜单可进入；
2. P1 事件处置主闭环可从头点到尾；
3. H5 可模拟核心移动操作；
4. 指挥态势展示 Mock 人员、物资和视频；
5. 演练、打卡、盘点各有一个简单闭环；
6. 无明显死链接或流程中断；
7. 保存少量截图或演示记录，并在本 README 说明启动方式；
8. 明确停止继续堆叠功能，转入第三关正式架构、数据、接口和测试设计。

以下不属于 Prototype Definition of Done：真实数据库/后端、RBAC、OAuth/SSO、Redis/MQ/微服务、生产部署、真实外部平台接入、压力或安全测试、完整单测体系和正式 CI/CD。

## 8. 开发顺序与治理

后续应按 `tasks.md` 的 G2-P02 → G2-P03 → G2-P04 执行。开始任何代码工作前，必须再次核对本 README、SRS、`docs/work/B_TECH/spec.md`、RTM、事实/数字控制文件和开放 Issue。发现真实需求矛盾时，只登记 Issue/澄清/变更，不在原型中静默改写需求。

每次原型走查均应区分“Mock 交互可演示”与“正式需求已验证”。截图、演示记录和页面—FR 映射是第三关设计输入，不是性能、接口、安全或验收证据。

## 10. G2-P03 核心流程原型

G2-P03 在 G2-P02 页面骨架上加入共享的 localStorage 状态和五条可点击闭环。使用驾驶舱右上方“重置演示数据”可恢复初始场景。

### P1 事件处置闭环

1. 从 H5“事件上报”创建事件；
2. 进入 Web“事件管理”执行核实通过；
3. 启动已发布预案，系统生成两项 Mock 任务；
4. 进入 H5“我的任务”确认接收、提交反馈并完成任务；
5. 回到 Web 查看任务和事件时间线，然后关闭事件；
6. 在“指挥态势”查看事件、任务、人员、物资站和视频占位。

追踪：G2-FR-001—004、013—016、021—022。启动用时只作为本地交互，不构成 KN-003 等性能验收证据。

### P3—P5 辅助闭环

- 演练：Web/H5 将演练从待执行推进到执行中、待评估和已完成，并形成模拟改进项；追踪 G2-FR-010—012、023。
- 打卡：H5 可分别模拟有效扫码和超出范围的拒绝结果，Web 展示记录；追踪 G2-FR-017—020、024。
- 盘点：H5 提交现场数量并自动计算差异，Web 复核后更新台账数量；追踪 G2-FR-008—009、025。

### 验证命令

```powershell
cd prototype
npm run test:smoke
npm run build
```

`test:smoke` 会从重置数据开始执行事件、任务、演练、打卡和盘点领域动作，并验证状态和数量结果。真实接口、性能、安全、部署和现场验收仍在原型范围之外。


## 11. G2-P03 复核整改

事件关闭现在具有双重门禁：所有关联任务必须完成，并且评估结论、调查记录和报告名称必须填写保存。关闭材料完成后，时间线显示材料保存和事件关闭记录；页面持续标注这些内容为 Mock。

打卡管理增加“模拟检测缺卡/超时”。检测后生成 Web 异常提醒和统一消息 Mock 记录；首次发送失败时进入待重试，重试仍失败时进入人工处置。该过程只验证页面与状态语义，不表示真实消息通道、并发或到达率已经验证。

- `prototype/evidence/G2-P04/`
